# 04 — Changing and authoring worlds

World selection is independent of avatar selection. The same avatar can be used in multiple worlds, and different avatars can use the same world. The API/action vocabulary stays unchanged unless a new controller or interaction design explicitly versions it.

## Four world kinds

| Kind | Authoring route | Reset behavior |
| --- | --- | --- |
| `room` | Native reference room in `ResearchEnvironment.cpp` | Reset capsule and seed the reference obstacle |
| `home` | Native instanced home in `ResearchHome.cpp` | Reset capsule and seed the courtyard crate |
| `layout` | Geometry entries in profile JSON | Reset capsule; pieces remain static |
| `map` | Authored Unreal level package | Reset capsule only; authored map state remains as-is |

`home` and `room` are fixed source recipes. Change their code and rebuild if you want to modify those exact recipes. Use `layout` or `map` for world changes without recompiling the plugin.

## JSON geometry

You can export the **existing home**, not just create a replacement from scratch:

```powershell
python -m erl.manage export-layout --instance default --profile configs/bob_home.json --output configs/my_home_snapshot.json
```

This authenticated read copies the running home/layout's primitive transforms, materials and collision flags into a new portable `layout` profile. It refuses to overwrite an existing file or use a base profile that differs from the running one. Edit that new file, stop the old instance and launch it with `--profile`. The current crate position becomes a fixed piece: this intentionally changes seeded-crate reset semantics into a static geometry snapshot. The generated profile and actual sensor evidence identify that new condition. This is not an export of arbitrary authored-map assets, scripts or dynamic state. The included `configs/bob_home_edit.json` is a ready example exported from the reference home; copy it to make your own revision.

Copy `configs/manny_layout.json`. Keep its avatar or replace it independently. Change `world.pieces`, spawn and map bounds. For example:

```json
{
  "position_cm": [300, 150, 50],
  "size_cm": [100, 60, 100],
  "rotation_deg": [0, 20, 0],
  "shape": "Cube",
  "material": "Oak",
  "collision": true
}
```

The position is the piece's center. An ordinary box with height 100 centered at z=50 rests on a floor at z=0. Use positive dimensions. Rotation is pitch/yaw/roll in degrees. Decorative foliage can disable collision; solid walls, floors and work surfaces should keep it. Repeated mesh/material/collision combinations use instanced components to reduce overhead.

Layout mode supplies the reference daylight rig. Its fills are a low-cost visual approximation, not physically calibrated light transport. Agent exposure and observer exposure are separate profile conditions. For custom lighting and richer assets, use an authored map.

After changes, stop the instance, validate the new profile, launch it and run contract/visual checks. The editor does not watch or hot-reload profile files during an experiment.

## An authored Unreal world

1. In an authoring project compatible with UE 5.8.3, create a level. Start with a conventional non-World-Partition level for the simplest portable test.
2. Build the static geometry, correct collision, lighting and asset references. Verify performance in Unreal. Set the intended spawn region clear of walls/props and provide a floor.
3. Save the map, e.g. `/Game/Maps/MyResearchWorld`. Keep its dependencies in their original package locations. If it uses plugin content, enable the needed plugins in the isolated harness. Do not copy a `.umap` alone and expect all references to resolve.
4. Add the authoring project's Content directory to machine `content_roots`, mount it as `/Game/`, and set `world.kind: map` and `world.map` to that package path.
5. Set spawn, initial heading, overview position and diagnostic bounds in the profile. Those are research settings; ERL does not infer them from a `PlayerStart`.
6. Run validate/doctor, launch, and inspect the loaded level and collisions. ERL first loads the engine entry map, registers external mounts after initialization, then opens the requested map before spawning the control actor.

The supplied `manny_map.json` uses a local `/EmbodiedResearch/Worlds/FixtureLab` generated by preparation. It provides an authored-map integration example without requiring another researcher's content. It is not a replacement for testing your own world.

## Static reset boundary

`map` mode does **not** rewind arbitrary actors, physics objects, doors, timers, weather, random Blueprint logic, external services or a task state machine. Its specification explicitly reports an avatar-only reset scope. Repeating seed/action sequences is meaningful only if all other relevant conditions are held fixed.

For a mutable research world, add an explicit reset adapter before calling it reproducible: it must enumerate state, seed all relevant generators, restore transforms/velocities and object states, cancel/reset timers, reset task/reward/termination providers, and confirm completion before exposing reset observations. That adapter and interaction semantics belong to the next research increment; this version does not silently pretend they exist.

No physics/gravity locomotion is supplied by the capsule adapter. Stairs, slopes, jumps, moving platforms, sitting and grasping need appropriate controllers. Visual geometry alone does not make an affordance usable.

## World acceptance

Check floor height, capsule clearance, wall/prop collisions, camera clipping, units and scale, illumination, texture/groom memory, valid image captures and reset repeatability. Check that the top-down map is labeled as a diagnostic bounds/trajectory view; for custom maps it does not invent a floor plan or expose positions to the policy. Record layout/map and asset revisions separately for training/validation/test conditions when those tasks are introduced.
